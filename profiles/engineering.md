# Profile: engineering

For projects that ship a feature list: applications, libraries, extensions, tools. The
work is "build this, make it correct, keep it working" — not "test this hypothesis and
find out".

Read [METHODOLOGY.md](../METHODOLOGY.md) and [RULES.md](../RULES.md) first. This file
says only what the profile adds and what it switches off.

---

## What it adds

| File | Size | Role |
|------|------|------|
| `conventions.md` | ≤300 | Code style, build, test, what must not be auto-formatted |
| `subsystems/<name>.md` | grows | Compiled knowledge about one part of the tree |
| `references/<spec>.md` | — | External specs, upstream state, third-party formats |

### `conventions.md`

Everything about "how code is written *here*" — the part a linter config does not
already say, and the part an agent will otherwise get subtly wrong.

- Naming: functions, variables, constants, types, files.
- Formatting: indentation (state it explicitly if it is unusual — three spaces will be
  "corrected" to four by every tool that touches it), line length, alignment.
- Comments: which language they are written in, when to write one, when not to.
- Build and test commands, dev and release, and **what counts as broken**.
- Workflow: what to check before a commit; which files to touch carefully; which files
  are generated and must never be hand-edited.

The most valuable section is usually the last one. "Do not reformat `vendor/`", "this
file is generated by the build", "the C engine is not touched without asking" — each of
those prevents a specific, expensive mistake, and none of them is visible in the source.

### `subsystems/<name>.md`

A focused page on one isolated part of the tree: the build, the localisation layer, one
module, one engine. It exists to keep noise out of the main files and to be loaded only
when the task touches that part.

Split a subsystem out when its documentation passes roughly 50–80 lines, or when an
agent should load it only for that area of work. Contents: purpose, the files that make
it up and their roles, the concepts specific to it, the interfaces it exposes to the
rest, and the nuances that only matter here. Link the related `G##` and `A##` entries
rather than restating them.

### `references/<spec>.md`

External knowledge — a file format specification, a third-party API's real behaviour,
an excerpt from a standard. This is not about your code; it is about the world your code
lives in.

For a fork, `references/upstream-watch.md` earns its place quickly: date, the range of
upstream commits reviewed, and the verdict. Without it, every session re-checks the same
range, or none of them does.

## What it switches off

The registers and machinery of the [research profile](research.md): `experiments.md`
(`E##`), `corpus.md`, `plan/`, and the measurement contract. Lint checks 9–16 are
inactive; hard rules H6–H9 do not apply.

**`journal.md` stays on.** It is core, not research-specific — it is where "why the work
went this way" lives once it has been evicted from `status.md`, and the eviction is what
keeps `status.md` inside its 80-line limit.

If the project starts producing hypotheses and measurements — a performance push, a
tuning constant nobody can justify, a "which of these three approaches is actually
faster" question — turn the research profile on for that work rather than letting the
answers dissolve into `architecture.md`. That is exactly how the `E##` register came to
exist.

## The situational guide

The single highest-value thing in an engineering project's `start.md`. It maps a
*situation* to the files worth loading:

```markdown
## What to read when

- **First time here** → overview → conventions → gotchas
- **Changing the UI or mode logic** → subsystems/ui.md; for progress changes also [[G01]] and [[A09]]
- **Changing the native engine or crypto** → subsystems/engine.md + conventions ("don't touch without asking")
- **Touching the build** → [[A01]]–[[A06]] + [[G02]]
- **Adding a string or a language** → subsystems/localisation.md
- **Anything performance-related** → [[A15]] + [[G17]], [[G18]], [[G20]] *before* you start
- **Before a refactor** → architecture.md + status.md (Fragile points)
```

Three things make a guide good:

1. **Every line is a real situation**, not an abstract category. "When working with
   variables" helps nobody; "adding a string or a language" is a task someone actually
   has.
2. **It points at anchors, not just files.** `[[A02]]` costs one entry to read;
   `architecture.md` costs the whole file.
3. **It connects gotchas to the work that triggers them.** The reader who is about to
   touch the intercept layer should be handed `[[G07]]` by the guide, not required to
   read the register in full and notice it.

What not to put in it: anything already obvious ("when changing code → conventions.md"),
a duplicate of the documentation map (the map lists files; the guide lists situations),
and one line per file just to be complete.
